## 三、AC-36 · 1 万条用户列表现场验收

**要求**：管理端用户列表在 1 万条数据下响应 < 1.5 s。

**方法**：压测库灌至 **10032 个用户**，用管理员页面会话请求真实页面视图 `GET /manage/users/?page_size=20`（不是 API），预热后连续测 5 次。

```
用户总数: 10032 | 管理员: perf_admin
状态: 200 | SQL 条数: 12
耗时 ms: [33.5, 31.6, 33.0, 33.5, 36.8]
平均 33.7ms | 最大 36.8ms
```

**结论：通过（33.7 ms ≪ 1500 ms，余量约 44 倍）。**

SQL 分布（12 条，无 N+1）：

| 条数 | 说明 |
|---|---|
| 2 | 取当前页 20 行用户（含 `select_related` 关联字段），Django 分页会先取 id 再取全量 |
| 1 | 当前页学生学科聚合（一次 `students__in` 查询，覆盖整页） |
| 1 | 行政班下拉（`annotate(Count)` 一次算完） |
| 2 | 分页 `COUNT(*)` |
| 1 | 唯一的启用管理员（页面「最后一个管理员不可停用」提示用） |
| 其余 | 会话 / 权限 / 表结构等固定开销 |

最慢单条 SQL 10 ms（启用管理员查询），无随行数增长的多余查询——**说明列表页架构是常数查询**，这与 `test_query_count_is_constant` 的断言一致。

## 四、热点与观察

1. **`POST /exams/{id}/start/` 是最慢端点**（20 用户下 3.1~3.4 s，3 用户时 157 ms）。它做的是：校验考试状态与时间窗 → 校验/创建 attempt → 计算 `deadline_at` → 组卷下发。**开考瞬间的读峰值本质上是这个接口的写+读混合**，优化优先看它。
2. **`GET /attempts/{id}/paper/` 是读峰值主体**（107 次请求，P95 3500 ms）。它要拼装整张试卷的题目 payload（含选项、知识点）。若后续要做生产级优化，这里是缓存或预生成的主要候选。
3. **并发劣化明显**：同样代码，3 用户时 135 ms，20 用户时 2426 ms（约 18 倍）。开发服务器单进程无法并行处理，这既说明服务端有串行瓶颈，也说明**该换 gunicorn 多 worker 才能得到真实数字**。
4. **`GET /grading/queue/` 619 ms 偏高**（仅 2 次请求，样本小）。它按 `Answer.is_correct__isnull` 拉待批列表并聚合，可能缺复合索引。建议在真实数据量下复测后再决定。
5. **失败率全程 0**，说明在该并发下没有出现连接池耗尽、锁等待超时或 5xx。

## 五、复跑方法

### 5.1 准备压测库

```bash
cd /d/OnlineExam
# 建库 + 12 学生 + 2 账号 + 20 题客观卷 + 1 场进行中考试
./.venv/Scripts/python.exe scripts/perf_seed.py setup --students 12

# AC-36 用：灌 1 万用户
./.venv/Scripts/python.exe scripts/perf_seed.py users --count 10000

# 用完丢弃（脚本有硬护栏：库名解析为 online_exam 会直接退出，不会碰演示库）
./.venv/Scripts/python.exe scripts/perf_seed.py cleanup --drop-db
```

### 5.2 起服务（务必 mock AI）

```bash
DB_NAME=online_exam_perf AI_PROVIDER=mock \
./.venv/Scripts/python.exe manage.py runserver 127.0.0.1:8024 --noreload
```

### 5.3 跑压测

```bash
# 场景 A：并发交卷
./.venv/Scripts/locust.exe -f scripts/locustfile.py --headless \
  -u 20 -r 5 -t 30s --only-summary --host http://127.0.0.1:8024 ExamSubmitUser

# 场景 B：开考读峰值
./.venv/Scripts/locust.exe -f scripts/locustfile.py --headless \
  -u 20 -r 5 -t 30s --only-summary --host http://127.0.0.1:8024 ExamStartBurstUser

# 场景 C：判分（无 AI）
./.venv/Scripts/locust.exe -f scripts/locustfile.py --headless \
  -u 3 -r 1 -t 10s --only-summary --host http://127.0.0.1:8024 ExamGradingUser
```

### 5.4 账号与限流说明

locustfile 优先读 `scripts/.perf_tokens.json`（由 `perf_seed.py` 用 `RefreshToken.for_user` **离线签发**）。

这不是偷懒——登录接口有 `auth` 限流（30/min，按 IP 计），压测全部来自 127.0.0.1，**逐用户真实登录会在第 30 次之后集体 429**，压测结果直接失真。没有 token 文件时才退回 `PERF_STUDENTS` + `PERF_PASSWORD` 走真实登录。

## 六、结论

| 项 | 结果 |
|---|---|
| 并发交卷（20 用户） | 184 请求，**0 失败**，6.36 RPS |
| 开考读峰值（20 用户） | 193 请求，**0 失败**，6.90 RPS |
| 判分（3 用户） | 8 请求，**0 失败** |
| AC-36（1 万条列表） | **33.7 ms**，通过（阈值 1500 ms） |
| 数据污染 | 无（压测全程使用 `online_exam_perf`，演示库未写入） |

**待改进（非阻塞）**：压测应在 gunicorn + 多 worker 下重跑一遍才有生产参考价值；`/exams/{id}/start/` 与 `/grading/queue/` 是两个值得优化的热点。
