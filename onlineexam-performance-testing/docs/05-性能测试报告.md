# 性能测试报告

> 被测系统：`D:\OnlineExam`（Django 4.2.30 + DRF + MySQL 5.6.46，Windows 单机）
> 压测工具：Locust 2.47.0；执行日期：2026-11-06
> 验收口径：一个班 **50 人并发**；环境口径：runserver / waitress / waitress+连接复用 三组对照

---

## 一、结论摘要

**一句话**：系统本身没有写坏的代码，慢的原因是**每个请求都重开一次 MySQL 连接**；
把连接复用打开后，50 并发从 12.8 RPS / P95 3.8 s 提升到 **45.2 RPS / P95 0.84 s**，交卷、读峰、判分、混合四个场景全部达标。

| 场景（50 并发） | runserver | waitress | **waitress+连接复用** | 阈值 |
|---|---|---|---|---|
| A 并发交卷（逐步爬升） | 12.2 RPS / P95 5700 ms ❌ | 12.8 / 3800 ❌ | **45.2 / 840 ✅** | P95 < 1000 |
| A′ 交卷洪峰（50 人同时点） | 11.8 / 5700 ❌（1.9% 失败） | 11.7 / 5100 ❌ | 31.1 / 2600 ❌ | P95 < 1000 |
| B 开考读峰（同时拉卷） | 13.0 / 4300 ❌（1.05% 失败） | 11.5 / 4100 ❌ | **33.1 / 1000 ✅** | P95 < 1500 |
| C 教师判分（10 并发） | 4.5 / 500 ✅ | 4.7 / 340 ✅ | **5.0 / 130 ✅** | P95 < 800 |
| D 混合场景 | 11.4 / 5200 ❌ | 13.2 / 3400 ❌ | **44.1 / 520 ✅** | P95 < 1500 |
| 超载 100 并发 | 12.3 / 9800，**7.25% 失败** ❌ | 12.4 / 8200，0 失败 | 42.1 / 2200，0 失败 | — |

**唯一没达标的是「50 人同一秒点交卷」**：连接复用后平均 870 ms、P95 2600 ms（0 失败）。
把 waitress 线程数从 8 提到 16 重跑，P95 降到 1300 ms、平均 710 ms（`opt_submit50_t16`）。
说明这一档的瓶颈已经从数据库转成**线程池排队**，靠加线程 + 前端错峰可以解决（见 §7）。

## 二、环境与局限

| 项 | 值 |
|---|---|
| 机器 | Windows 11，Intel 4 物理核 / 8 逻辑核，15.8 GB |
| 服务 | runserver（开发服务器）／waitress 3.0.2（8 或 16 线程） |
| 数据库 | MySQL 5.6.46 本机，`innodb_buffer_pool_size=128M`，`skip_name_resolve=OFF` |
| 压测库 | `online_exam_perf`（独立库，未污染演示库） |
| AI | `AI_PROVIDER=mock` + 判分固定 `with_ai=false`，全程无真实大模型调用 |
| 数据规模 | 130 个学生账号、1 份 20 题客观卷、1 场考试、50 份待批作答 |
| 服务端配置 | `DEBUG=False`（压测专用配置），日志降级，无 DRF 调试渲染器 |

**必须写进结论的四条局限**：

1. **同机压测**：Locust 与被测服务抢同一批 CPU，数据只能看相对趋势，不代表生产绝对容量。
2. **单机单进程**：waitress 是线程模型（受 GIL 约束），等价于单核并行上限；生产上的多进程/多机容量需另测。
3. **无 HTTPS**：全部走明文 HTTP，TLS 开销未计入。
4. **AI 批改未压**：走 mock，AI 场景的耗时（外部大模型调用）不适用本报告任何数字。

## 三、关键发现

### 发现 1（主因）：每个请求重开一次 MySQL 连接

证据链：

| 观测 | 数据 |
|---|---|
| 单用户、带认证的接口耗时 | `GET /exams/` 约 90 ms；`GET /attempts/` 67-85 ms |
| 单用户、不带认证（401，不查库） | **2-3 ms** |
| 单用户 P50（同一基线用例） | runserver 91 ms → waitress 67 ms → **连接复用 39 ms** |
| MySQL 新建连接（PyMySQL 实测 5 次） | **51.6 / 63.7 / 65.0 / 67.0 / 69.0 ms** |
| 同一连接上执行查询（10 次） | 0.08-0.21 ms |
| 服务端 CPU（50 并发时） | 仅 **13%**（约半核） |

结论：一个请求的 70-90 ms 里，**绝大部分花在建连握手**，业务 SQL 只占零点几毫秒。
原因有两层——Django 默认 `CONN_MAX_AGE=0`（请求结束就关连接），而 MySQL `skip_name_resolve=OFF`
（每次连接都做一次反向域名解析，Windows 上这一下就要几十毫秒）。

这也解释了阶梯曲线为什么是这个形状：50 并发只有 12.2 RPS ≈ 1/0.082 s，**建连被串行化了**，
并发越高只是排队越长，TPS 不涨。

### 发现 2：换 WSGI 服务器几乎没用，但开发服务器会丢连接

waitress 8 线程与 runserver 的 TPS 差在 5% 以内（12.8 vs 12.2），说明瓶颈不在服务器模型。
但两者在**瞬时建连**上的差别很明显：

- runserver：100 并发 79 次失败（7.25%）、50 人瞬时交卷 20 次失败（1.92%），错误全是 `status=0`（连接被拒/重置）；
- waitress：同样负载 **0 失败**。

所以「生产别用 runserver」这条结论依然成立，只是它解决的是**稳定性**，不是**速度**。

### 发现 3：`GET /grading/queue/` 随作答数线性变慢

| 待批作答数 | 接口耗时 |
|---|---|
| 50 份 | 0.86 s |
| 1629 份 | 10.5-12.3 s |

第一次跑判分场景时，10 个教师用户全卡在这个接口里，90 秒内一条判分请求都发不出去（`req=0`）。
当前规模（一个班 50 份）下 0.86 s 尚可接受，但**一场考试结束后如果教师不逐个批完，列表会越来越慢**，
而管理端列表（AC-36）1 万条只要 33.7 ms——差距说明这个接口是逐条处理而不是聚合下推。

## 四、逐场景结论

**A 并发交卷（50 人陆续进入，爬升 5/s）**
runserver 与 waitress 都是 P95 3.8-5.7 s，不可用；连接复用后 45.2 RPS / P95 840 ms，0 失败，**达标**。

**A′ 交卷洪峰（50 人同一秒点交卷）**
即使调优后 P95 仍 2600 ms（平均 870 ms，0 失败）。原因是 50 条连接在同一秒建立，
8 个工作线程排不过来。加到 16 线程后 P95 1300 ms、吞吐 40.4 RPS。**建议 threads=16 + 前端随机错峰 0-3 s**，
两件事做完这一档就能进 1 s。

**B 开考读峰（50 人同时刷新拉卷）**
调优后 33.1 RPS / P95 1000 ms，**达标**。接口拆分里最重的是 `POST /exams/{id}/start/`（P50 1500 ms），
其次是 `GET /attempts/{id}/paper/`（P50 260 ms、P95 1000 ms）——开考瞬间的瓶颈是「组卷下发」，
不是读卷面。这符合上一轮的判断，值得后续单独优化（见 §7）。

**C 教师判分（10 并发，50 份待批）**
三组口径都达标，调优后 P95 130 ms。判分本身很轻，之前的 1.6 s 全部来自队列列表接口。

**D 混合（交卷/读峰/判分 3:3:1）**
最接近真实考试日的组合。调优后 44.1 RPS / P95 520 ms，0 失败，**达标**。

**稳定性（50 并发 15 分钟）**
35178 请求 0 失败，P95 从 717 ms 漂到 695 ms（-3%），RSS 108.8→110.1 MB（+1.2%），连接数稳定在 50。
**无内存泄漏，无随时间劣化。**

## 六、失败分析

三组口径累计失败 114 次，**全部来自 runserver**，且 100% 是 `status=0`（连接被拒/重置），
没有一条是业务码错误（`code != 0`）。分布：100 并发 79 次、50 人瞬时交卷 20 次、50 人读峰 12 次、混跑 3 次。
waitress 与连接复用两轮 **0 失败**。

这说明：在这些并发下，业务逻辑没有出现竞态、唯一约束冲突或次数超限这类问题；
失败纯粹是开发服务器的连接承载能力不够。

## 七、建议（按性价比排序）

1. **开连接复用**：`CONN_MAX_AGE=60`（配合 `CONN_HEALTH_CHECKS=True`）。一行配置换来 3.5 倍吞吐，收益最大。
2. **MySQL 加 `skip_name_resolve=ON`**（`my.ini` 改完重启）。这是建连慢的根因，改掉后即使不复用连接也能快一大截；
   代价是 `GRANT` 里只能用 IP/`%`，不能用主机名。
3. **生产别用 runserver**：Linux 上用 gunicorn（`workers = 2*核数+1`）+ nginx；Windows 上 waitress `threads=16`。
4. **交卷错峰**：前端在「点击交卷」后随机延迟 0-3 s 再发请求，把 50 人的瞬时洪峰摊平，
   这是成本最低的一招（不需要改后端）。
5. **`/grading/queue/` 加约束**：强制分页（默认 20 条/页）+ 把统计字段改成聚合查询或冗余列，
   避免一场考试积累上千份后教师端打不开。当前 1629 份要 10 s。
6. **`/exams/{id}/start/` 值得单独优化**：它同时做状态校验、attempt 创建、组卷下发，
   开考瞬间 P50 就 1500 ms。建议用 `assertNumQueries` 数一下 SQL 条数，先排 N+1。
7. **加监控**：至少要有慢查询日志（`long_query_time=0.5`）和接口 P95 看板，
   否则这类"每请求重连"的问题只能靠压测偶遇。

## 八、与上一轮（2026-10-27）的关系

上一轮 20 并发、runserver、30 秒，结论是「3 用户 135 ms → 20 用户 2426 ms，劣化 18 倍，建议换 gunicorn」。
本轮把那条结论往前推了一步：**劣化的原因是数据库连接不复用，不是 WSGI 服务器**——
换 waitress 后 50 并发依然是 12.8 RPS，而只改一行 `CONN_MAX_AGE` 就变成 45.2 RPS。
上一轮的报告已归档在 `docs/00-历史基线-模块11性能测试报告.md`，两轮数据可对照。

## 九、复跑方法

> 核心工程在 `D:\onlineexam-performance-testing\onlineexam_performance_testing`，命令都在这里执行。

```bash
cd /d/onlineexam-performance-testing/onlineexam_performance_testing

# 1) 数据（隔天跑先 --refresh-only：刷新时间窗并重签 token；重建则用 --students）
D:/OnlineExam/.venv/Scripts/python.exe scripts/seed.py --refresh-only
D:/OnlineExam/.venv/Scripts/python.exe scripts/seed.py --students 130 --reset-attempts

# 2) 起服务 + 跑一轮（自带起停，跑完自动关）
D:/OnlineExam/.venv/Scripts/python.exe scripts/run_with_server.py \
    --mode waitress --threads 8 --conn-max-age 60 \
    --suite waitress-conn60 --resume

# 3) 只跑某几个 / 看进度
D:/OnlineExam/.venv/Scripts/python.exe scripts/run_with_server.py \
    --mode waitress --threads 16 --conn-max-age 60 \
    --suite waitress-conn60 --only submit50 --label-suffix _t16
D:/OnlineExam/.venv/Scripts/python.exe scripts/progress.py

# 4) 重新汇总
D:/OnlineExam/.venv/Scripts/python.exe scripts/summarize.py > report/summary.md
```

每轮原始数据在 `onlineexam_performance_testing/report/`，同名用例重跑以最后一行为准。
