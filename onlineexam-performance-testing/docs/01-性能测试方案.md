# OnlineExam 性能测试方案（Locust 选型 + 测试流程）

> 被测系统：`D:\OnlineExam`（Django 4.2 + DRF + MySQL 5.6，Windows 本机）
> 前置测试：功能测试 `D:\毕设\exam-fun-test`、接口测试 `D:\onlineexam-api-autotest`、UI 测试 `D:\onlineexam-ui-autotest`
> 本方案定位：**简单性能测试**——不追求极限容量，回答三个问题：能扛多少人、慢在哪、有没有明显缺陷（泄漏 / N+1 / 锁）。

---

## 1. 结论：用 Locust

一句话理由：**项目里已经有可用的 Locust 脚本和数据准备脚本，选 Locust 是"接入"而不是"从零建设"；选 JMeter 等于把这套东西重写一遍，且换不来任何本项目需要的能力。**

`D:\OnlineExam\scripts\` 下已有：

- `locustfile.py`：三个场景类，`ExamSubmitUser`（并发交卷）、`ExamStartBurstUser`（开考读峰值）、`ExamGradingUser`（教师批量判分）
- `perf_seed.py`：`setup` / `users --count 10000` / `cleanup [--drop-db]` 三个子命令，独立压测库 `online_exam_perf`，产出 `.perf_meta.json` 和 `.perf_tokens.json`
- `requirements.txt` 已声明 `locust>=2.47`，venv 实测 `2.47.0` 已安装

### 1.1 选 Locust 的具体理由

1. **脚本资产可复用**：三个场景、JWT 登录、逐题暂存、交卷、心跳、判分链路都写好了，连"登录接口 30/min 限流会导致虚拟用户 429"这种坑都提前绕过了（用 seed 离线签发的 token）。改造成本接近 0。
2. **技术栈一致**：接口测试是 pytest + requests，断言风格、账号数据、接口封装思路可以直接搬。JMeter 是另一套 DSL（JSON 提取器 + JSON 断言 + CSV 参数化 + 线程组），要在 GUI 里重新表达一遍同样逻辑。
3. **压测即代码**：`locustfile.py` 能进 Git、能 Code Review、能参数化、能写业务断言（脚本里已经在用 `catch_response` 校验 `code != 0`）。JMeter 的 `.jmx` 是 XML，改一行要开 GUI，评审只能看截图。
4. **报告够用**：`--headless --csv` 出原始数据、`--html` 出图表，Web UI 实时看曲线，答辩演示足够好看。
5. **扩展路径清楚**：日后要真上生产量级，`--master/--worker` 多机分布式只加命令行参数，不用重写脚本。

### 1.2 为什么不用 JMeter

JMeter 的优势是**零编码 + 协议广 + 报告成熟**：录制回放生成脚本、支持 JDBC/LDAP/WebSocket/JMS、GUI 里拖一拖就能跑。但放到这个项目上，这些优势基本落空：

- 本项目全是 HTTP + JSON 接口，没有 JMeter 独占的协议需求；
- 团队只有一个人（你），且是 Python 技术栈，"不会写代码才用 GUI"这个前提不成立；
- JMeter 的 GUI 本身吃内存，真正压测必须用 `-n` 命令行模式，图形化的好处只剩"生成脚本"，而脚本本来就有；
- `.jmx` 的可维护性差，后期改接口路径、加断言都要开 GUI，时间成本高于改 Python。

**什么情况下我会反过来推荐 JMeter**：需要给非技术方演示、需要按 Selenium/录制方式零代码出脚本、需要压 JDBC 直连数据库、或企业内已有 JMeter 平台和报告规范要遵循。以上都不是本项目的约束。

### 1.3 要不要再做一次 JMeter 对照？（可选，不必要）

如果答辩材料需要体现"多工具能力"，可以只挑**一个**接口（比如 `POST /attempts/{id}/submit/`）用 JMeter 跑 50 并发，和 Locust 的结果比对 TPS 与 P95。目的是证明结论不受工具影响，不是证明 JMeter 也适用于全流程。此事优先级最低，时间不够直接砍掉。

## 2. 前置条件核查（已做 vs 待补）

**已就绪**

- 压测脚本、造数脚本、独立压测库设计（含"库名等于演示库就报错"的保护）
- 30 个压测学生 + 1 教师 + 1 场进行中考试的种子数据，`.perf_meta.json` 已生成（考试 ID=1，密码 `Perf@123456`）
- 离线 token 池，规避 `auth` 限流 30/min

**待补（本次要做的）**

1. **性能测试报告文档缺失**：`docs/进度记录.md`、`docs/项目交付说明.md` 都引用了 `docs/性能测试报告.md`，但 `docs/` 下实际没有这个文件。本次补一份完整的、带曲线和复跑命令的报告。
2. **压测口径是开发服务器**：现有数据来自 `manage.py runserver`（单进程、`DEBUG=True`）。`DEBUG=True` 会记录每条 SQL，压测数字偏悲观且不可信。需要新增一个 `OnlineExam/settings/perf.py`（`from .development import *` 后置 `DEBUG=False`），并用 `--noreload` 起服务。
3. **需要生产近似的 WSGI 服务器**：Windows 用不了 gunicorn，装 `waitress`（`pip install waitress`），`--threads=8` 起 8 线程。做"单进程 runserver vs 多线程 waitress"两组对照，才能回答"到底是框架慢还是部署方式慢"。
4. **监控采集**：Django 侧无 APM，用 MySQL 慢查询日志 + `SHOW PROCESSLIST` + 系统计数器兜底（见 §4）。

**硬性约束（每次执行都要守）**

- 压测库 `online_exam_perf`，绝不指向 `online_exam`
- `AI_PROVIDER=mock`，判分脚本固定 `with_ai=false`，避免真实调用烧钱
- 只压本机 `127.0.0.1`，不对外网地址发压
- 压测账号全部用 seed token，不走登录接口

## 3. 测试目标与验收阈值

性能测试的价值一半在脚本，一半在**先定阈值**。以下阈值按"学生点击到出结果的可感知上限"反推，你可以按答辩需要调整：

**场景 A｜并发交卷（`ExamSubmitUser`）**

- 50 并发持续 3 分钟：错误率 = 0，P95 < 1000ms，TPS 不低于 20
- 关注点：`Answer` 的 `update_or_create` 是否行锁排队、`ExamAttempt` 收尾 UPDATE 是否超时

**场景 B｜开考拉卷峰值（`ExamStartBurstUser`）**

- 100 并发瞬时冲击（spawn rate 拉满）：错误率 < 0.5%，P95 < 1500ms
- 关注点：`GET /attempts/{id}/paper/` 会重建整份卷面（选项、已存答案、乱序计算），是本系统最重的读，最容易暴露 N+1

**场景 C｜教师批量判分（`ExamGradingUser`）**

- 10 并发：P95 < 800ms，错误率 0
- 关注点：`GradingService.recalc` 是否全量重算、是否成为长事务

**场景 D｜AC-36 管理端列表（已有基线，复核即可）**

- 1 万用户首屏 < 1500ms（历史记录 33.7ms），12 条 SQL 无 N+1

**全链路通用**

- 错误率 < 0.5%（业务码 `code != 0` 也算失败，不只是 HTTP 5xx）
- 服务端 CPU 均值 < 80%，无持续内存增长（30 分钟 soak 内 RSS 漂移 < 10%）
- MySQL `Threads_connected` 不持续上涨，无 > 0.5s 慢查询

## 4. 要采集的指标

**压测端（Locust 自带）**：并发数、RPS/TPS、P50/P90/P95/P99、最大值、失败数与失败原因分类、按接口拆分的统计（脚本已用 `name=` 归一化路由，如 `POST /attempts/[id]/submit/`，能把动态 ID 聚合成同一个接口）。

**服务端**：CPU / 内存（任务管理器或 `typeperf`）、Django 进程 RSS 走势、MySQL `Threads_connected` / `Questions` / `Innodb_row_lock_waits`、慢查询日志（`long_query_time=0.5`）。

**业务侧（容易漏但最能说明问题）**：交卷后 `ExamAttempt` 状态是否正确、答案是否落库、判分分数是否算对。性能测试把系统压出脏数据，比压慢更严重。

## 5. 测试流程（按阶段执行，每阶段有产出才进下一阶段）

### 阶段 0｜环境搭建（半天内）

```bash
# 1) 装依赖（在 D:\OnlineExam 下）
./.venv/Scripts/python.exe -m pip install waitress

# 2) 造压测数据（会建库 online_exam_perf，跑完可 --drop-db 丢弃）
./.venv/Scripts/python.exe scripts/perf_seed.py setup

# 3) 起压测服务：独立端口 8024，DEBUG 关掉，AI 走 mock
DB_NAME=online_exam_perf AI_PROVIDER=mock DJANGO_SETTINGS_MODULE=OnlineExam.settings.perf \
  ./.venv/Scripts/python.exe manage.py runserver 127.0.0.1:8024 --noreload
```

**产出**：能跑通的环境 + `.perf_meta.json`（30 学生 / 考试 ID / token）
**通过标准**：浏览器或 curl 用 `perf_stu_001` 能登录、能开考、能拉到卷面。这一步不过，后面全是脏数据。

### 阶段 1｜基准单接口（baseline）

单用户、单请求循环，摸清每个关键接口的"裸"耗时，作为容量估算和后续对比的基准。

```bash
./.venv/Scripts/locust.exe -f scripts/locustfile.py ExamStartBurstUser \
  --headless -u 1 -r 1 -t 60s --only-summary --host http://127.0.0.1:8024
```

**产出**：关键接口基线耗时清单（`/auth/login/`、`/exams/`、`/exams/{id}/start/`、`/attempts/{id}/paper/`、`/attempts/{id}/answers/`、`/attempts/{id}/submit/`、`/grading/queue/`、`/grading/attempts/{id}/grade/`）
**通过标准**：每个接口在 1 并发下 P95 < 200ms（除判分）。超过的先查 SQL，别急着加压。

### 阶段 2｜容量阶梯（找拐点）

固定场景，按 10 → 20 → 50 → 100 → 200 逐档加压，每档 3-5 分钟，档间冷却 30 秒并重置数据。

```bash
for U in 10 20 50 100 200; do
  ./.venv/Scripts/locust.exe -f scripts/locustfile.py ExamSubmitUser \
    --headless -u $U -r 5 -t 3m --only-summary \
    --csv report/step_$U --html report/step_$U.html \
    --host http://127.0.0.1:8024
done
```

**产出**：并发-TPS-响应时间三张曲线，找出 **TPS 拐点**（再加并发 TPS 不涨）和 **错误率突增点**。
**通过标准**：拐点并发数 > 业务预期峰值（按一个班 50 人同时考试估算，50 并发即达标）。

### 阶段 3｜业务场景压测

把"考试当天真实发生的三件事"各压一遍，这是报告的主指标：

- **A 交卷洪峰**：0 → 50 并发瞬时（`-r 50`），持续 3 分钟。模拟下课铃响全班同时交卷。
- **B 开考读峰**：0 → 100 并发瞬时，持续 2 分钟。模拟开考瞬间全体刷卷。
- **C 判分批处理**：10 并发，持续 3 分钟，教师侧批量判分。

**产出**：三个场景的完整报告（csv + html + 失败明细）
**通过标准**：§3 的阈值全部满足；失败明细里不允许出现 5xx 和数据不一致。

### 阶段 4｜稳定性（soak）

中等负载（30 并发）连续跑 30-60 分钟，看指标是否随时间漂移。

**产出**：RSS / 连接数 / P95 随时间的走势图
**通过标准**：P95 前后段差异 < 20%，无内存单调上涨，MySQL 连接数回落到基线
**这一阶段的真正目的**：抓"交卷累积导致 paper 接口越来越慢"这类只在长时间运行后暴露的问题。

### 阶段 5｜瓶颈定位

对阶段 2/3 里最慢的接口逐个查：

1. **SQL 层**：慢查询日志、`SHOW PROCESSLIST`、`Innodb_row_lock_waits`；对 `/attempts/{id}/paper/` 用 `assertNumQueries` 或 `django.db.connection.queries` 数 SQL 条数，确认有没有 N+1
2. **代码层**：判分是否全量重算、simplejwt 是否每请求查一次 user 表、序列化器是否带嵌套
3. **部署层**：runserver 单进程（GIL 下等价单线程）本身就是最大瓶颈之一，用 waitress 对照即可证明

**产出**：瓶颈清单（接口 + 证据 + 推测原因 + 影响面），按"改起来便宜且收益大"排序
**通过标准**：至少定位出 1 个具体瓶颈，并能用数据说明它在总耗时中的占比

### 阶段 6｜调优验证（只做 1-2 项，别陷进去）

每轮**只改一个变量**，改完重跑阶段 2 的目标档位，出 before/after 对比：

- 候选一：runserver → waitress `--threads=8`（零代码改动，通常收益最大）
- 候选二：给最慢接口加 `select_related` / `prefetch_related` 或补索引
- 候选三：关掉 `DEBUG`、去掉不必要的中间件

**产出**：调优前后对照（同一个并发档位的 TPS 与 P95）
**通过标准**：改动后指标有可量化提升，且功能测试套件仍全绿（防止压测优化改坏业务）

### 阶段 7｜出报告

`docs/06-性能测试报告.md`，结构固定：

1. 测试环境（机器规格、Python/Django/MySQL 版本、部署方式、并发工具版本）
2. 测试范围与场景设计（三个场景各压什么、怎么建模的）
3. 阈值与结论（逐条对照，达标/不达标写清楚）
4. 曲线与数据（并发-TPS、P95 走势、soak 内存曲线）
5. 瓶颈分析与证据
6. 调优前后对比
7. 遗留风险与建议（比如"生产需 gunicorn + 多 worker 重跑"）
8. 复跑命令（照抄就能复现，答辩时很有用）

## 7. 已知风险与坑（提前写下来，避免踩第二遍）

1. **同机压测**：Locust 和服务端抢同一块 CPU，客户端并发超过 200-300 时自身可能成为瓶颈（GIL）。解决：200 并发以上时记录客户端 CPU，必要时 `--processes` 或多机；报告里必须声明"客户端与服务端同机，数据偏保守"。
2. **`DEBUG=True` 会让数据失真**：每条 SQL 都进内存日志。压测必须 `DEBUG=False`，且用 `--noreload`（否则文件监视器干扰）。
3. **数据累积影响可比性**：交卷场景每轮都会新增 `ExamAttempt`，第 5 档和第 1 档的数据量不同。每档之间跑 `perf_seed.py cleanup` 重建，或固定跑 N 轮后统计。
4. **限流**：`auth` 30/min 按 IP，所有虚拟用户都是 127.0.0.1。必须用 seed token，别在 `on_start` 里循环登录。
5. **AI 调用**：判分固定 `with_ai=false` + `AI_PROVIDER=mock`，双保险。一旦真调大模型，耗时不可复现且产生费用。
6. **Windows 上限**：gunicorn 不可用，只能用 waitress（线程模型，不是多进程）。真要测多进程需 WSL/Linux 或 `uvicorn` + 多 worker，超出"简单性能测试"范围，报告中作为建议项即可。
7. **别把性能测试做成调优项目**：毕设阶段目标是"测得准、说得清、有结论"，不是把系统优化到极致。阶段 6 最多做 2 项。

## 8. 已确认的决定（2026-11-06）

1. **环境口径：三组对照**。`runserver`、`waitress --threads 8`，外加 `waitress + CONN_MAX_AGE=60` 作为调优组。
   前两组回答「换服务器有没有用」，第三组回答「真正的瓶颈在哪」。
2. **并发规模按一个班 50 人算达标**。同时保留 100 并发一档，用来看超载时的错误率拐点，不作为验收线。
3. **不做 JMeter 对照**。

### 落地时对流程的两处调整（执行中发现，脚本已改进）

- **判分场景改为冻结名单**：压测中交卷会把作答数推到上千份，而 `GET /grading/queue/` 随作答数线性变慢
  （50 份 0.86 s、1629 份 10.5 s），教师用户全卡在列表接口，判分动作一条都发不出去。
  改为预置 50 份待批卷 + 冻结 attempt id 名单；队列列表的规模问题单独作为一条发现记录。
- **补了「数据准备」这一层**：被测项目的 `perf_seed.py` 不建班级，教师创建的 `open_to_all` 考试对学生不可见
  （`/exams/` 为空、`start/` 404）。在压测侧 `scripts/seed.py` 里补班级与次数上限，被测项目一行未改。
