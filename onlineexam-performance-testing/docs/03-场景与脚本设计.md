## 二、三个场景怎么建模的

### 场景 A · 并发交卷 `ExamSubmitUser`

真实场景是「下课铃响，全班同时点交卷」。所以：
- **爬升 = 并发数**（`-r 50 -u 50`），而不是慢慢加人；
- 每个虚拟用户一个循环 = 开考 → 逐题暂存 → 交卷 → 立刻开下一轮，保证"持续有人交卷"的稳态；
- 权重 4:1 里带心跳，模拟前端每 30 秒上报剩余时间。

覆盖的写路径：`ExamAttempt` 创建/收尾 UPDATE、`Answer` 的 `update_or_create`（带唯一约束冲突）。

### 场景 B · 开考读峰 `ExamStartBurstUser`

真实场景是「开考瞬间，全班同时刷新页面拉卷子」。所以 6:2:2:1 的权重压：
- `GET /attempts/{id}/paper/`（最重：重建整份卷面，含选项、已存答案、乱序计算）
- `GET /exams/{id}/`、心跳、`GET /attempts/`

### 场景 C · 教师判分 `ExamGradingUser`

交卷本身不触发判分，判分是教师/后台独立动作，所以单独压
`POST /grading/attempts/{id}/grade/`（固定 `with_ai=false`）。

**判分名单要冻结**：压测中交卷场景每分钟造出上千份 attempt，而
`GET /grading/queue/` 的耗时随作答数增长（实测 50 份 0.86 s、1629 份 10.5 s）。
不冻结的话，10 个教师用户全卡在 `on_start` 的队列请求里，90 秒内一条判分请求都发不出去
（第一轮就踩到了：`req=0`）。冻结后判分场景 P95 从 1.6 s 降到 0.34 s，才是判分本身的耗时。
队列列表的规模问题单独记录，不混进场景结论。

## 三、断言设计

只有 HTTP 200 不算通过——DRF 统一响应体里 `code != 0` 也是失败：

```python
if resp.status_code != 200:
    resp.failure(f"暂存失败：{resp.status_code}")
elif (resp.json() or {}).get("code") != 0:
    resp.failure(f"暂存业务错误：{resp.text[:120]}")
```

`/attempts/{id}/paper/` 额外校验 `questions` 非空，防止"接口 200 但卷面是空的"这种假通过。

## 四、服务端指标怎么采的

Django 侧没有 APM，所以 `run_case.py` 起一个采样线程，每 2 秒记一次：

- 进程 CPU（`psutil.Process.cpu_percent`，除以逻辑核数换算成整机占比）
- 进程 RSS（判断内存泄漏，soak 阶段主要看它）
- 到被测端口的 ESTABLISHED 连接数（判断有没有连接堆住/泄漏）

统计时丢掉前 10% 样本（预热），避免启动阶段拉低均值。

## 五、踩过的坑（都已在脚本里处理，别再踩一遍）

1. **系统代理会吃掉压测**：本机设置了 `HTTP_PROXY/HTTPS_PROXY`，requests 会把
   `127.0.0.1` 的请求也发给代理，直接 502。`run_case.py` 给 Locust 子进程剔除了代理变量并设 `no_proxy`。
2. **`resp.failure()` 只能在 `catch_response=True` 里调用**：被测项目原脚本的开考失败分支少了这个参数，
   失败时会抛 `AttributeError`，把「404 开考失败」伪装成脚本异常，真实原因被吞掉。
3. **单用户基线必须先跑**：本机 MySQL 新建连接 52-69 ms、复用后查询 0.1 ms，
   单用户与并发下的差距几乎全部来自连接开销——不先测基线会误判成"业务代码慢"。
4. **同机压测**：Locust 与被测服务抢同一批 CPU，客户端并发高时自身也会成为瓶颈（GIL）。
   报告里的数字一律注明「同机、单机」，只能看相对趋势。
5. **数据规模会影响结论**：作答记录会累积。判分场景必须冻结名单，
   否则第二轮的阈值和第一轮不是一回事。
