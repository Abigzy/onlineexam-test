## 0. 结论摘要（先给结论）

| 项 | 结论 |
|---|---|
| **整体可行性** | **可行**。技术栈无阻断项，关键路径已用真实浏览器跑通（§5.4 实测证据） |
| **建议范围** | 35 条路由中取 **26 条**做自动化（覆盖三角色 13 条业务主链路 + 权限可见性），排除纯图表看板与 AI 内容质量类页面（§6） |
| **规模预估** | 约 **140 条** UI 用例（P0 约 30 / P1 约 65 / P2 约 45），冒烟子集 ≤ 8 分钟 |
| **技术选型** | Python 3.11 + Selenium 4.38 + **Chrome 156（headless=new）** + pytest + Allure + **PO 模式**；数据构造走 `/api/v1/`，断言走 DOM 事实 + 只读 SQL |
| **三条硬约束** | ① 必须**显式指定** chromedriver 156（PATH 上是 143，直接实例化会 `SessionNotCreated`）；② 列表/卡片/表格都是 **JS 注入**，必须显式等待节点，`readyState=complete` 不算加载完成；③ 造数必须带 `UIAT_` 前缀并自动清理，不污染 52 用户 / 701 题演示库 |
| **最大风险** | 时间依赖（倒计时 / 30s 宽限 / 考试时间窗）> CDN 首屏慢（jsdelivr 单文件 9~35s）> 动态渲染等待缺失导致的假失败（详见 §8 R-01~R-14） |
| **不建议自动化** | ECharts 像素级比对、AI 生成内容质量、移动端 375px（已由 `UI走查清单` 覆盖 44/44）、性能压测 |

一句话：**这套系统的 UI 层适合做"业务主链路 + 交互行为 + 权限可见性"的回归自动化，不适合做"渲染效果"的自动化。**

## 2. UI 架构分析（决定自动化技术选型）

### 2.1 渲染模式：服务端骨架 + JS 注入内容（**最重要的一条**）

页面 HTML 只给出骨架，列表/卡片/表格/弹窗内容由 `fetch` 拉 `/api/v1/*` 后 `innerHTML` 注入。例：

- `exam/index.html:142` → `box.innerHTML = rows.map(cardHtml).join('')`
- `questions/bank.html:326` → `tbody.innerHTML = data.results.map(rowHtml).join('')`

**后果**：`document.readyState == 'complete'` 只代表骨架就绪，节点还没出现。断言前必须等**业务节点**（如 `#exam-cards .card`、`tbody tr` 非"加载中"态），否则会得到"随机假失败"——这是 UI 自动化最常见的翻车点，本方案把它写成 PO 基类的统一等待契约（步骤 5）。

### 2.2 认证：表单 POST，不是接口 token

登录页是标准 Django `{% csrf_token %}` 表单（`input[name=username]` / `input[name=password]` / `button[type=submit]`）。因此：

- 登录用例走**真实表单**（这是 UI 层不可让渡的验证点）；
- 其余用例可在 `session` fixture 里用 `requests` 表单登录取 `sessionid`，再用 `add_cookie` 注入浏览器——**省掉每条用例 1.6s 的登录开销**（实测单次登录 1.60s，140 条用例可省约 3.5 分钟）。

### 2.3 前端依赖 CDN：首屏慢且受网络影响

Bootstrap 5 / Bootstrap Icons / ECharts 全部走 `cdn.jsdelivr.net`，`UI走查清单 §5.4` 记录**单文件 9~35s**。应对：固定 `--user-data-dir` 做磁盘缓存（走查脚本已验证有效），否则 140 条用例的总时长不可控。

### 2.4 交互形态盘点（决定 PO 的组件封装）

| 形态 | 出现页面 | 自动化要点 |
|---|---|---|
| Bootstrap Modal | 交卷确认 `#submitModal`、新建考试 `#examModal`、新建班级 `#classModal`、越权 `#permModal` | 必须等 `show` 类/`display:block`，不能只等元素存在（DOM 里常驻） |
| 页签切换 | 我的考试 `#tabs`、批改工作台、学情看板 | 点击后等内容重渲染，断言"激活态 + 内容变化"两者 |
| 树形结构 | 知识点管理 | 需展开父节点后才能定位子节点 |
| 文件上传 | 题库导入 | `send_keys(绝对路径)`；需准备 `.xlsx` 夹具 |
| 文件导出 | 试卷导出（`window.open`） | 会产生新窗口句柄，需 `window_handles` 切换 + 断言 URL，**不断言文件内容**（接口层已覆盖） |
| 倒计时/心跳 | 答题页 `#timer` / 心跳 30s | 时间敏感，只断言"存在且在递减"，不赌具体秒数 |
| ECharts 画布 | 5 个页面 | 只断言 `canvas` 存在 + 容器有数据，不断言图形 |

### 2.5 状态与时间语义（设计用例时的红线）

- `deadline_at` 由**服务端**在开考时算好并落库，前端倒计时只做展示（FR-6-1）；
- 超时交卷留 **30 秒宽限**（`SUBMIT_GRACE_SECONDS`），UI 上无法稳定命中这一秒级窗口；
- 考试状态"进行中"是**按时间实时算**（`computed_status()`），不落库；
- 结论：**凡是"等它超时"的用例不放进 UI 层**，改由接口层构造过期尝试后回 UI 验错误态。

## 4. 业务主链路（UI 自动化真正要守的东西）

页面层的价值不在"能不能打开"（走查已覆盖 251 个检查点），而在**跨页面的状态流转是不是对的**。

| 编号 | 链路 | 起点 → 终点 | 关键断言（UI 可见事实） |
|---|---|---|---|

## 5. 自动化可行性评估

### 5.1 技术可行性：**通过**

| 维度 | 评估 | 依据 |
|---|---|---|
| 框架匹配 | Selenium 4.38（系统 Python 3.11）可直接驱动 Chrome 156 | 实测启动 2.39s |
| 会话建立 | 表单登录可脚本化，1.60s/次 | 实测 [3] |
| 连续点击 | **Chrome 稳定**（Edge headless 有"连点两次崩 msedgedriver"的历史坑） | 实测 [6][7]，两次真实点击均成功 |
| 动态内容 | JS 注入需显式等待，技术上完全可控 | 实测卡片/图表均能取到 |
| 报告 | Allure 2 + `allure-pytest`，Windows 下需 `allure serve` 或生成静态 HTML | 待步骤 4 落地 |

### 5.2 元素定位可行性：**总体通过，但有 3 个必须提前定策略的点**

- **360 个 id / 141 个 data-*** → 核心交互控件（弹窗、按钮、筛选器）基本都有 id，PO 可以直接引用，不需改被测代码。
- **零 id 的 5 个页面** → 用 `name` 属性（表单）、语义 class（`.empty-state`、`.alert-danger`）与文案定位；不引入 XPath 绝对路径。
- **风险点 1**：`exam/index.html` 里存在 JS 拼串生成的 id（`id="' + item.id + '"` 形式），这类"动态 id"不能写死在 PO 里 → 统一改用 `class + data-*`。
- **风险点 2**：Modal 常驻 DOM，`find_element` 一定能找到，断言必须看可见性（`is_displayed()` / `.show` 类）。
- **风险点 3**：表格行是 `innerHTML` 拼的，**没有稳定 id**，定位靠 `tbody tr:nth-child(n)` → 用例设计时避免依赖行序号断言业务值，改用"按文本找行"。
- **纪律**：全程 `By.CSS_SELECTOR` 优先，禁止 `//div[3]/div[2]` 这类绝对路径；定位器集中写在 Page 类顶部常量区，便于页面改版时一处修。

### 5.3 测试数据可构造性：**可，但必须走 API 造数**

UI 造数（点页面建数据）慢且脆弱，本方案定为：**业务数据用接口造，UI 只做"读"和"改"，并保留 2~3 条纯 UI 造数的端到端链路**（T-1、T-4、A-1）作为"UI 能建数据"的证据。

需要的造数清单（步骤 3 落地）：

| 数据 | 数量 | 造法 | 备注 |
|---|---|---|---|
| 学生 / 教师账号 | 各 2（+1 备用） | `POST /api/v1/auth/register/`（学生）+ 管理员建教师 | 用户名带 `UIAT_` 前缀 |
| 知识点 + 题目 | 1 树 + 6 题型各 1 | `POST /knowledge-points/`、`POST /questions/` | 覆盖六种题型渲染差异 |
| 试卷（含三层结构） | 2 | `POST /papers/` + `random-compose` | 一份含主观题（验 AI 批改入口）、一份纯客观 |
| 考试（进行中 / 已结束 / 未开始） | 3 | `POST /exams/` + 改 `deadline_at` | 时间窗按"开考后 +3h"造，避免过期（接口项目踩过：+60min 造数 1 小时后全挂） |
| 作答 + 成绩 | 2（1 已批改、1 待批改） | `POST /attempts/{id}/save/` + `finalize` | 成绩单/证据链页依赖 |
| 班级（本班 / 他班） | 2 | `POST /classrooms/` | 越权用例依赖 |
| 导入夹具 | 1 个 `.xlsx` | 仓库内固定夹具 | 题库导入用例 |

清理策略：所有数据带 `UIAT_` 前缀 / 固定 ID 段，用例结束按 ID 精确删除，**不做全表清理**。

### 5.5 稳定性与可重复性风险（按"会不会造成假失败"排序）

| 编号 | 风险 | 表现 | 应对 |
|---|---|---|---|
| R-01 | 动态渲染未就绪 | 断言时节点还不存在 → 随机失败 | PO 基类统一等待"业务节点 + 非加载中" |
| R-02 | CDN 首屏慢 | 首次打开 9~35s，偶发超时 | 固定 `user-data-dir` 缓存；`page_load_timeout=60` |
| R-03 | 时间依赖 | 倒计时、30s 宽限、考试窗过期 | 造数时窗放宽到 +3h；超时类用例不进 UI 层 |
| R-04 | 演示库数据被污染 | 用例互相干扰、第 2 次跑失败 | `UIAT_` 前缀 + 精确清理 + 用例内不依赖"列表第 1 行" |
| R-05 | AI 真实外呼 | 慢（几十秒）、花钱、不稳定 | 只测入口与降级；批量回归不点"AI 批改/生成" |
| R-06 | 弹窗常驻 DOM | 断言"元素存在"恒真 → 漏测 | 断言可见性 + 遮罩态 |
| R-07 | 新窗口（导出） | 断言跑到旧窗口 | 显式 `window_handles` 切换 |
| R-08 | 浏览器/驱动错配 | 直接起不来 | 驱动随工程入库 + 启动自检版本 |
| R-09 | 轮询页面数据自变 | 监控页断言值漂移 | 只断言结构与"有数据"，不断言具体数字 |
| R-10 | 全屏/切屏事件 | 影响 `#btn-fullscreen`、`cheat-banner` | 这类用 JS 事件模拟，不赌浏览器全屏行为 |
| R-11 | 中文文本断言 | 文案微调即失败 | 关键文案抽到常量，允许包含匹配而非全等 |
| R-12 | 多用例并发 | 同一学生账号考试态互串 | 串行执行 + 账号分组，不做并行 |
| R-13 | 服务未重启 | 改了代码仍验旧行为（接口项目踩过） | 执行前 `--noreload` 重启 + `/api/health/` 探活 |
| R-14 | Allure 环境缺失 | 报告生成为空 | 生成静态 `allure-report/`，不依赖 `allure serve` |
