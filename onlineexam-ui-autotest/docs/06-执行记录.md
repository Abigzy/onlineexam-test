## 1. 分层执行策略

执行不是"跑一遍 pytest"，而是按**变更影响面**分三档，每档有独立的触发条件、耗时预算和放行门槛。这套口径来自 `02-测试计划与策略.md` §7，执行阶段只做落地和校准。

**SMK 冒烟（15 条，≈1.5min）**　命令 `pytest scripts/test_l0_smoke.py`。
覆盖三角色登录 + 9 个核心页首屏 + 核心权限（学生不能进题库/考试管理、教师不能进管理端）。
触发时机：任何对 `common/` 或 `pages/` 的改动之后、提测前、每天第一轮。
**门槛：必须 15/15 全绿**，一条红就停，不允许"先跑完再说"——冒烟红了说明框架或环境坏了，后面 139 条的结果没有参考价值。

**REG 回归（135 项，≈19min）**　命令 `pytest scripts/test_l1_*.py`。
11 个业务域全量业务流：认证 14、题库 20、试卷 14、考试作答 20、考试管理 12、判分 11、学情 8、班级 6、管理端 8、权限 9、学情练习 13。
触发时机：被测业务代码有变更、每日一次。
**门槛：红项必须定位到"脚本问题 / 环境问题 / 产品问题"三者之一**，脚本问题当场修，产品问题进 `缺陷管理.md`。

**FULL 全量（154 项，≈18min）**　命令 `pytest`（`testpaths=scripts`）。
在回归基础上加 15 条冒烟（会重复执行，作为独立回归证据链）和 4 条缺陷守卫（`scripts/test_regressions.py`，纯接口 3.7s，BUG-01/02 复发即红）。
触发时机：版本发布前、阶段收口。
**门槛：`151 passed / 3 skipped / 0 failed` 且 skip 名单与白名单逐条一致**，退出码 0。

**slow 白名单**　`-m "not slow"` 是默认行为，被排除的 3 条（`UI-EXAM-21/22/23`：填空自动暂存、刷新保留答案、简答题落库）依赖 `AUTOSAVE_INTERVAL_SECONDS=30`，单条要真等 30s+。要看它们时 `OE_SLOW=1 pytest -m slow`。**"默认不跑"不等于"不覆盖"**——本轮已在 `OE_SLOW=1` 下单独验证过一次，三条均通过，只是不进日常档位。

**每档执行后的固定动作（必做）**　`pytest.ini` 带 `--clean-alluredir`，pytest 一启动就清空
`report/allure-results`（连 `environment.properties` 一起）。因此**跑完任何一档都要立即重新生成报告**：

- `pytest` 一条命令即可：收尾自动生成并打印
  `[auto-report] 154 条 / 6.3s -> …/uireport.html`（**默认开启**，见 README 纪律 11）
- 手工补生成（自动失败时的兜底）：`bash tools/gen_report.sh` 或 `python tools/gen_report.py`
- 只想跑用例、不要报告：`OE_AUTO_REPORT=0 pytest -q`

生成后核对三件事：入口是 `uireport.html`（目录里不该有 `index.html`）、`[OK] 用例数` 与本次收集数一致、
报告首页 ENVIRONMENT 区有 8 项。**不做这一步，`allure-report/` 里就是上一轮的旧结果**——页面能开、
数字却过期，这种"看起来有报告"比报错更容易误导。

## 4. 稳定性分析

### 4.1 一致性

判断"稳"的标准不是一次全绿，而是**同一范围连跑两轮，通过数一致、耗时偏差可控**：

- 冒烟：83.80 → 85.07（+1.5%）
- 回归 L1（分 5 段）：132 passed / 3 skipped，与全量里 L1 部分一致
- 全量 154：FULL-08 `151P/3S / 1206.40s` ↔ FULL-09 `151P/3S / 1068.86s`，通过数完全一致，墙钟 −11.4%；
  连同 FULL-07（同代码基线 1082.73s）看，三次数值是 1082.73 / 1206.40 / 1068.86，**FULL-08 是偏慢的一轮**（+11%），不是用例变慢
- 分批：认证 +0.02s、学情练习 +1.04s、班级 +0.42s、权限 −0.42s、管理端 −3.21s、学情 −1.44s

### 4.2 flaky 清零路径（三类"假绿/假红"）

这是本次执行最有价值的部分。三类问题**不会稳定复现**，只在全量串跑时偶发，靠"再跑一次"永远修不掉，必须从等待契约上解决：

**第一类：双视图中间态（会假绿）**。组卷页 `loadPaper()` 先 `applyHead()` 写卷头统计、再 `renderSheet()` 渲染卷面，只等标题与题库池就会出现"卷头 3 题、卷面 0 个 `.paper-q`"的窗口。FULL-05 唯一失败点 `test_add_question_from_picker`（断言 0→4，实际造数卷 3 题）就是它。修法：`open_paper()` 等 `.paper-q` 有卡片或出现「还没有题目」，`add_picked()` 以加题前 `#metaCount` 为基准等卷头与卷面**同时**到位。由此立下纪律 10：凡是"计数 ↔ 列表""标题 ↔ 明细"的双视图，等待条件写**两者相等**。

**第二类：初值是占位文案（会假绿）**。`#c-name` / `#metaCount` / `#poolBody` 的模板初值分别是「加载中…」「—」「加载中…」。只等"非空"永远成立，页面还没请求完就已经"过了"。修法按页面各自改成等终态信号：班级详情等 `#c-name` 脱离「加载中…」、班级列表等 `.card` 数量、创建/加人等 **toast**（「班级已创建」「已加入」）而不是等弹窗 `display:none`（Bootstrap fade 有 300ms 过渡，`display` 早于视觉消失）。

**第三类：断言读不到真值（会假红/假绿）**。两处踩过：① `wait_url("/classrooms/")` 用子串匹配，`/classrooms/173/` 提前命中，删班后"已跳回列表"是假的 → 改 `re.fullmatch(r".*/classrooms/?", url)`；② 导航断言用 `.text` 读 Bootstrap 下拉菜单，`display:none` 时永远是空串，"学生看不到题库入口"这条差点变成永远为真的假绿 → 改读 `#mainNav` 的 `textContent`。

**另外一类不算 flaky 但表现像"随机失败"**：同页多表单时用全局 `button[type=submit]`。个人中心页同时有「保存资料」「修改密码」和导航里「退出登录」三个 POST 表单，全局选择器命中第一个，点下去直接被踢回登录页。修法：选择器锚定业务表单 `form:has(input[name="action"][value="profile"]) button[type="submit"]`。

### 4.3 耗时曲线

单位成本 `wall / items` 九轮分别是 7.36 / 7.28 / 7.36 / 7.42 / 7.38 / 7.33 / 7.08 / 7.83 / 6.94 秒，中位数 **7.36s**。**没有随规模劣化**——说明没有"越跑越慢"的资源泄漏（driver 每条都 `quit()`、session 级造数只做一次）。要提前估一轮多久，按 **7.5s × 条数**算就够：加 10 条约 +75s。

FULL-07 → FULL-08 墙钟从 1082.73s 涨到 1206.40s（**+11.4%**），但**用例体只涨了 4.6%**（433.5s → 453.5s），多出来的 ~100s 全在夹具/驱动层；紧接的 FULL-09 又回到 1068.86s（比 FULL-07 还快 1.3%），**说明 FULL-08 那 +11% 是环境抖动，不是用例退化**——同一台机器连续跑 6 小时的 Chrome 起停与 MySQL 冷热差异足以造成这个量级的漂移。这也是监控要同时看"墙钟"和"用例体"两个数的原因：只看墙钟会把环境噪声误判成用例变慢。

单条最慢的是 `test_last_page_next_disabled` **132.1s**（题库 701 题分页，末页要翻 30+ 页），占用例体总耗时 `431.6s` 的 **30.6%**。有优化空间（直接跳末页 `?page=N`），但它是 P1 且只跑一次，暂不动——**先保正确，再谈快**。

### 4.4 时间构成与提效空间

用例体 `431.6s` + 其余 `637s`。这 637s 基本是**每条用例一个 Chrome 进程**的代价：起停约 2s、`_inject()` 打开 `/login/` 写 cookie 约 1.5s、夹具造数/清理若干。三条可选路径：

1. **driver 提为 class 级**：一个测试类共用一个 Chrome（约省 30%），代价是类内用例会串味（前一条留下的筛选条件、滚动位置、未关弹窗），需要每条用例显式 `reset()`。风险中等，收益明确。
2. **xdist 并行**：收益最大（4 进程≈4 倍），但固定 `--user-data-dir` 直接冲突，要给每个 worker 独立 profile 与独立造数命名空间；MySQL 5.6 上并发写入虽不像 SQLite 那样整库锁，但同一份造数（`runtime`/`bank`）被子进程共享会打架，得先做数据分片。现实收益会打折。
3. **不动**：18 分钟对"发布前跑一次"完全够用。

结论：**本轮不优化**。当前耗时不影响任何准出判断，而 1/2 都会引入新的 flaky 风险——这正是 §4.2 花大力气消灭的东西。

### 9.5 报告生成自动化（`OE_AUTO_REPORT`）

"每轮跑完必须重新生成报告"已经写进 README 纪律 11、§1 固定动作与 `pytest.ini` 注释，但它终究靠人记。
本轮加了自动开关，最初的默认值是**关闭**（后来改为默认开启，见 §9.6）：

```
OE_AUTO_REPORT=1 pytest -q
…
[auto-report] 154 条 / 6.3s -> …/report/allure-report/uireport.html
```

**当时默认关的理由**：报告每轮自动重建，人就不再关心它到底有没有更新，反而弱化对"是否最新"的判断；
本地开发时手工跑一次更清楚。CI / 交接这类"没人记得手动执行"的场景再打开。

实现上刻意做了三件事：

1. **逻辑只有一份**。新增 `common/report_builder.py`（写环境信息 + generate + 改名），
   `tools/gen_report.py` 与 `conftest.py` 的自动触发都调它。此前 `gen_report.sh` 里有一套独立的
   bash 实现（`cat > environment.properties`），正是 `Run` 写死的根源——两份实现必然两种口径。
   现在 `.sh` 只剩挑 Python 解释器并转调，`bash tools/gen_report.sh` 与 `python tools/gen_report.py`
   输出完全一致，均打印 `[OK] 用例数 154`。
2. **挂在 `pytest_unconfigure` 而非 `pytest_sessionfinish`**。后者要和 terminalreporter 抢钩子顺序，
   实测输出会插在 `1 passed in 6.3s` 汇总行之**前**，看着像"没跑完就出报告"；unconfigure 在汇总之后，
   `[auto-report]` 落在最末。`quiet=True` 顺手吞掉 JVM 的
   `Report successfully generated to …`，不让它污染 pytest 输出。
3. **绝不改退出码**。生成失败只打一行警告（`[auto-report] 失败：…`）并写 WARNING 日志，
   用例通过就是通过；`--co` 与空结果目录直接跳过——此时没有可生成的东西。

验证做了四组，都是实测不是推断：

| 场景 | 命令 | 结果 |
|---|---|---|
| 开 | `OE_AUTO_REPORT=1 pytest …::test_student_login_lands_home` | `1 passed` + `[auto-report] 1 条 / 5.3s`，退出码 0；报告 1 条，`Run=2026-11-06 00:10:07 ~ 00:10:09 [tag 11060010]` |
| 关 | 同上不加变量 | `uireport.html` 的 mtime **未变**，输出里 `auto-report` 出现 **0 次** |
| `--co` | `OE_AUTO_REPORT=1 pytest -q --co` | 收集 154 项，报告未重建（跳过分支生效） |
| 失败分支（函数级） | `build()` 指向不存在的 Allure CLI / 空结果目录 | 分别返回 `code=2` / `code=3` 并带 `msg`，**不抛异常** |
| 失败分支（端到端） | 把 `tools/allure-2.30.0` 临时改名后 `OE_AUTO_REPORT=1 pytest …` | `1 passed` + `[auto-report] 失败：找不到 Allure CLI…`，**退出码 0** |
| 改引用后复验 | 开关移入 `config.AUTO_REPORT` 后重跑 | `1 passed` + `[auto-report] 1 条 / 4.5s`，退出码 0 |

证据留了五份：`log/autoreport_{on,off,co,on2,fail}.txt`（各有 `EXIT_CODE=`）。
开/关两次的输出差异就是"报告是否真被重建"的直接证据——只看"能打开"是分辨不出来的。

**这里踩到一个必须记的坑：钩子形参 `config` 会遮蔽模块 `import config`。**
开关一开始写成 `config.AUTO_REPORT` 直接读，`pytest_unconfigure(config)` 的形参恰好就叫 `config`
（pytest 传进来的是 `Config` 对象），于是 `config.AUTO_REPORT` 变成
`AttributeError: 'Config' object has no attribute 'AUTO_REPORT'`。更糟的是守卫写在 `try` 之外，
异常冲出钩子，**整轮会话退出码变成 1**——用例全绿却报失败，这种"测试没问题、框架说有问题"
最难排查（当时 `1 passed in 6.43s` 与 `EXIT_CODE=1` 同时出现在同一份日志里）。

两处修正：钩子内改用 `import config as appcfg` 局部重命名；**守卫也挪进 `try`**——
钩子里的任何东西都不该有能力杀掉会话。教训是通用的：pytest 钩子的形参名（`config`、`session`、
`report`）与本项目模块名高度重合，写钩子前先确认有没有同名遮蔽。此前的 `allure-results_full8` 等轮次归档已删除——两轮对比的数字（1206.40s / 1068.86s）已固化在 §4.1，留目录反而容易和新结果混淆。

### 9.6 自动生成改为默认开启（`OE_AUTO_REPORT` 从"开启项"翻成"关闭项"）

起因是一次很直接的提问：`AUTO_REPORT = os.environ.get("OE_AUTO_REPORT") == "1"` 是不是已经开着？
答案是**没有**——变量没设时 `.get()` 返回 `None`，`None == "1"` 为 `False`，直接 `pytest` 不会出报告。
而"跑完必须重新生成"这条纪律恰恰是最容易漏的一步，把它留给记忆、把自动化留给一个没人记得加的环境变量，
等于默认关掉了唯一能兜住这件事的机制。于是反转默认值：

```python
AUTO_REPORT = os.environ.get("OE_AUTO_REPORT", "1").strip().lower() \
    not in ("0", "false", "no", "off")
```

实测解析表：未设 / `1` / `true` / 空串 → 开；`0` / `false` / `no` / `off` / `OFF` → 关。
现在 **`pytest` 一条命令就够**，报告随会话收尾落地；只在反复调单条用例、或 results 交给 CI 统一出报告时用
`OE_AUTO_REPORT=0` 关掉。

**顺手修掉一个更隐蔽的坑：`--alluredir` 的相对路径是相对 cwd 而不是 rootdir。**
`pytest.ini` 写的是 `--alluredir=report/allure-results`，pytest 原样交给 allure 插件、由后者按**当前工作目录**
建目录。于是在 `onlineexam-ui-autotest` 根目录敲 `pytest`，结果会写进根目录的 `report/`，而自动生成读的是
`onlineexam_ui_autotest/report/allure-results`——要么读到上一轮的旧结果、要么没结果直接跳过，两种情况都
**不报错**，只是报告悄悄过期。修法是 `conftest.py` 里加 `pytest_configure`，带 `tryfirst=True`（必须在 allure
插件自己的 configure 之前改：它在那一步初始化文件写入器，`--clean-alluredir` 的删目录也在那一步）把相对路径
按 conftest 所在目录求绝对。

两组实测都在**项目根目录**跑，也就是最容易出错的位置：

| 场景 | 命令 | 结果 |
|---|---|---|
| 默认（不设变量） | `pytest onlineexam_ui_autotest/…::test_anonymous_profile_redirect -q` | `1 passed in 6.39s` + `[auto-report] 1 条 / 13.5s -> …/uireport.html`，退出码 0；根目录**没有**多出 `report/` |
| 关闭 | 上述命令前加 `OE_AUTO_REPORT=0` | `1 passed in 7.21s`，输出里 `auto-report` 出现 **0 次** |

**又撞了一次纪律 8 的批量删除保护**：results 里有 168 个文件时直接 `pytest`，`--clean-alluredir` 的 `rmtree`
触发运行环境的批量删除保护，报 `INTERNALERROR … SystemExit: 1`（用例一条都没跑）。这不是新问题，是纪律 8
早就写明的，只是这次从"提醒"变成了"实测确认"——**每轮跑之前先 `mv report/allure-results` 归档、再 `mkdir`**，
是启动动作的一部分，不是可选项。

顺带修掉一处产物污染：本轮开始时发现 `report/allure-results` 只剩 42 条（时间跨 00:28:05~00:33:09，混着
单例验证的结果），并非交付基线的 154 条——上一轮收尾时它有被后续运行改写。该目录已按上述规程清空重建，
全量重跑后恢复为 154 条基线。

### 9.7 全量跑出一条新红：`UI-CLS-02` 成员数为 0（双视图时序，非产品缺陷）

改造后的第一次全量（FULL-10 前半段）出现 `1 failed / 150 passed / 3 skipped / 1252.30s`，
`test_own_class_detail` 断在「本班成员数为 0（前置不成立）」。先查数据、再查页面：

- **接口侧正常**：`GET /api/v1/classrooms/32/` → `student_count=24`，`/classrooms/32/students/` → `count=24`。
  不是造数被清、也不是权限问题。
- **页面侧问题**：班级详情页有两块内容来自**两个接口**——`#c-name` 来自班级详情，`#member-count` /
  `#member-list` 来自成员列表接口。`open_by_id()` 只等到 `#c-name` 不再是「加载中…」就返回，此时
  成员区仍是模板初值（「共 0 人」+ 空表），用例立刻读，自然读到 0。
- 结论：**脚本等待契约缺口**，不是产品缺陷；这条属于纪律 10 说的「计数 ↔ 列表」双视图，之前只在
  快机上侥幸通过。

修法：`ClassroomDetailPage.wait_members()` —— 等 `member_count > 0` **且** `== member_rows()` 才算就绪，
返回 `(count, rows)`；用例改成 `count, rows = detail.wait_members()`，断言仍留在用例侧（PO 只负责等，
不负责判）。超时由 `wait_for` 抛带 message 的断言，报告里能一眼区分「等不到」与「真为 0」。

验证：单跑连 **4 次全过**（5.74 / 5.85 / 5.87 / 6.11s）；随后全量复跑
**151 passed / 3 skipped / 0 failed / 1071.35s（17m51s）**，`[auto-report] 154 条 / 14.6s`，
报告 154 项、failed 0、ENVIRONMENT 8 项、`Run=2026-11-06 00:58:39 ~ 01:16:18 [tag 11060058]`。

教训：名字先到、列表后到的页面，等首屏 ready 就断言等于赌网络。凡有独立 fetch 的区域，
等待判据必须落在那块区域自己身上。
