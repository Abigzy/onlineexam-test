## 二、BUG-01 删除「被考试引用的草稿试卷」返回 500

| 字段 | 内容 |
|---|---|
| **缺陷标题** | 删除被考试引用的草稿试卷时服务端返回 500，而非 4xx 业务错误 |
| **环境/版本** | 本机 `127.0.0.1:8931`，Django 4.2.30，MySQL 5.6，2026-11-04 提测版 |
| **复现步骤** | 1. `POST /api/v1/papers/random-compose/` 建卷（记 id=P）<br>2. `POST /api/v1/papers/P/status/ {"status":"published"}`<br>3. `POST /api/v1/exams/ {"paper_id": P, ...}` 建一场引用该卷的考试（记 id=E）<br>4. `POST /api/v1/papers/P/status/ {"status":"draft"}` 把卷退回草稿<br>5. `DELETE /api/v1/papers/P/` |
| **预期结果** | 4xx + 业务错误码，提示「试卷已被考试引用，请先归档/删除相关考试」 |
| **实际结果** | `HTTP 500`，响应体 `{"code":50000,"message":"服务器内部错误，请稍后重试或联系管理员"}` |
| **严重程度** | 一般（数据未被破坏，但错误处理违反接口规范；UI 上表现为整页 500 错误页） |
| **优先级** | P1 |
| **影响范围** | 教师/管理员在「试卷与组卷」列表删除**任何已被考试引用的草稿卷**都会命中；`POST /papers/{id}/status/` 退回草稿后删除同样触发 |
| **复现率** | 3/3（`paper=425`、`429`、`432` 三次均稳定复现） |
| **附件** | `docs/assets/bug01_repro.txt`（受控复现脚本输出） |
| **定位线索** | 已发布状态删除会被业务层拦住（400 / code 13001「已发布的试卷不能删除」），说明校验只做了 `status` 判断，**没做引用检查**；退回草稿后直接落到 ORM 删除，`Exam.paper` 外键的保护/级联在删除时抛异常，被统一异常处理器兜成 500。建议：`PaperViewSet.destroy` 前查 `Exam.objects.filter(paper=obj).exists()`，命中抛 `BusinessError(code=13xxx)`；同时把 13001 的文案补上「或先处理引用它的考试」 |
| **状态** | **已关闭（2026-11-04 回归通过）**：返回 `400 / code=13008`，文案「试卷《…》已被 N 场考试引用，无法删除；如确需下线请改为「归档」，以保留考试与成绩的可追溯性」；试卷仍在。关闭依据见下节验证记录 |

### 修复说明（开发侧回填，2026-11-04）

| 项 | 内容 |
|---|---|
| **根因确认** | `PaperService.delete` 只判 `is_published`，**没查引用**。`Exam.paper` 是 `on_delete=PROTECT`，退回草稿后 status 那关形同虚设，直接 `paper.delete()` 抛 `ProtectedError`，被统一异常处理器兜成 500 |
| **改动** | 删除前查 `paper.exams.count()`，命中抛 `BusinessError(code=13008)`；`13001` 文案补上「若已被考试引用，还需先处理引用它的考试」 |
| **回归用例** | `apps/papers/tests/test_delete_reference.py` 5 条（完整 5 步复现 / 无引用可删 / **归档的考试仍拦截** / 已发布 13001 / service 层直调也被拦） |
| **实测** | `DELETE /api/v1/papers/430/` → `HTTP 400 / code=13008`，试卷保留 |
| **UI 表现** | 顺带修了 `UI.error(err)` 直接塞 Error 对象的问题（原来 toast 会显示「Error: …」前缀），现在展示的是纯业务文案 |
| **一个易误解点** | 提示语刻意**不建议「先处理考试」**——归档的考试仍然持有外键，试卷照样删不掉，唯一出路是归档试卷。原「对测试的影响」一节的描述与此一致 |

### 验证记录（2026-11-04 修复后）

| B 被引用 + 已发布 | 4xx + 13001（原行为不变） | HTTP 400 / 13001（文案已补「若已被考试引用，还需先处理引用它的考试」） | ✅ |
| C 无引用 + 草稿 | 删除成功（不能修过头） | HTTP 200 / code=0 | ✅ |
| D 无引用 + 已发布→退草稿 | 删除成功 | HTTP 200 / code=0 | ✅ |

- 验证脚本：`tools/verify_bug01.py`　｜　输出留档：`docs/assets/bug01_verify.txt`
- **回归守门**：`onlineexam_ui_autotest/scripts/test_regressions.py::TestClosedDefects`（2 条，纯接口、2.6s），
  已并入 `-m p1` 回归集；BUG-01 若复发会立刻红。
- 顺带修正：清理策略识别 13008 后直接归档，不再走"退草稿→再删"的无效路径。

## 三、BUG-02 题目编辑器保留空选项行提交，服务端 400 且提示不可读

| 字段 | 内容 |
|---|---|
| **缺陷标题** | 题库新增/编辑题目时，未填写的选项行被原样提交，导致保存失败且错误提示为 `[object Object]` |
| **环境/版本** | 本机 `127.0.0.1:8931`，Django 4.2.30，MySQL 5.6，2026-11-04 提测版 |
| **复现步骤** | 1. 打开 `/question-bank/new/`（默认题型=单选题，页面自动渲染 A/B/C/D 四个**空**选项行）<br>2. 只填题干 + 选项 A、B 的内容，勾选 A 为正确答案<br>3. 直接点「保存」 |
| **预期结果** | ① 只提交已填写的选项（空行被忽略），保存成功；或 ② 明确提示「第 3 行选项内容不能为空」，并高亮该行 |
| **实际结果** | 请求 `POST /api/v1/questions/` 返回 **HTTP 400**，前端 toast 显示：`options：[object Object]；[object Object]；[object Object]；[object Object]`（用户完全无法理解）。题目未创建，页面停在编辑页 |
| **严重程度** | 一般 |
| **优先级** | P1 |
| **影响范围** | 题库新增 / 编辑全部题型（选择类）。**默认就渲染 4 个空行，只填 2 行是最常见的操作**，触发概率高；有变通办法（填满或逐行删除） |
| **附件** | `docs/assets/bug02_repro.txt`（复现脚本 `tools/repro_bug02.py`，含前端 payload 与后端报文）；Allure 报告 `UI-QB-02` 用例记录 |
| **复现率** | 3/3 |
| **状态** | **已关闭（2026-11-04 验证通过）** — 8 项断言全通过，见本节「验证记录」 |

### 修复说明（开发侧回填，2026-11-04）

| 项 | 内容 |
|---|---|
| **修法** | **1 + 2 都做了**（按建议）；后端**没放宽** |
| **① 前端 collect()** | `templates/questions/editor.html` 的 `payload.options` 末尾加 `.filter(o => o.content)`——与 `validate()`（它本来就只统计"有内容的"）口径对齐。空行不再进 payload |
| **② UI.errorText()** | `static/js/api.js`：原来对数组直接 `String(item)`，嵌套结构必出 `[object Object]`。改为递归展平，**列表项标注序号**（用户要知道是第几行），内层对象只取文案不重复字段名 |
| **③ 后端** | **刻意不改** `QuestionOptionInputSerializer.content`（保持 `allow_blank=False`）。若为"修缺陷"把它改成 `allow_blank=True`，空行会静默入库，题库出现空白选项的脏数据。补了守门测试 `test_option_content_cannot_be_blank` |
| **实测（后端）** | 只提交 2 个选项 → `HTTP 201 / code=0`；带 2 个空行 → `HTTP 400`（确认该由前端过滤） |
| **实测（错误渲染）** | 缺陷里的真实报文 `{options: [{}, {}, {content:["该字段不能为空。"]}, {...}]}` → 现在渲染成 **`options：第 3 项：该字段不能为空。；第 4 项：该字段不能为空。`**（多字段时用空格分隔：`stem：请填写题干　options：至少需要 2 个选项`） |
| **为什么两层都要修** | 只修 ①：其他接口的嵌套错误仍然显示 `[object Object]`。只修 ②：用户填 2 行仍会看到两条"第 3/4 项不能为空"——提示可读了，但操作还是失败，体验依然差 |
| **未做** | 没做"自动删除空行"的 DOM 操作——用户正在填第 3 行时误点保存会丢输入。用过滤（忽略）而不是删除更安全 |

### 根因分析

两处叠加，缺一不可：

1. **前端** `templates/questions/editor.html::collect()`：
   ```js
   payload.options = Array.from(document.querySelectorAll('#options-list .option-row'))
       .map(row => ({ label: ..., content: row.querySelector('.option-content').value.trim(), ... }));
   ```
   没有 `filter(o => o.content)` —— 空行原样进 payload。而 `validate()` 只校验"有内容的选项 ≥ 2，且有正确项"，**放过了空行**。

2. **后端** `apps/questions/serializers.py::QuestionOptionInputSerializer`：
   `content = serializers.CharField()` 默认 `allow_blank=False`，于是每个空行返回一个错误对象；DRF 的错误是嵌套结构，前端 `UI.errorText()` 对数组直接 `String(item)` → `[object Object]`。

实测报文（`POST /api/v1/questions/`，HTTP 400）：

```json
{"code":40000,"message":"请求参数有误",
 "errors":{"options":[{}, {}, {"content":["该字段不能为空。"]}, {"content":["该字段不能为空。"]}]}}
```

注意前两个选项（A/B，已填写）在报文里是**空对象** `{}` —— 前端把它们也一起 `String()` 了，
所以 4 个空行对应 4 个 `[object Object]`。这说明错误渲染逻辑对"部分成功/部分失败"的嵌套结构完全没处理。

### 建议修法（任选其一，建议 1 + 2 都做）

1. 前端 `collect()` 里 `filter(o => o.content)`，只提交填写了内容的选项（对齐 `validate()` 的口径）；
2. 后端把错误结构展平，例如返回 `options: ["第 3 行选项内容不能为空"]`，或前端 `UI.errorText()` 支持嵌套数组/对象，取 `Object.values(err).flat().join('；')`；
3. 可选：单选项只填 2 行时，前端自动删除/忽略其余空行，避免用户手动删。

### 修复说明（开发侧，2026-11-04）

两处都改了，属于"双保险"：

1. **前端过滤空行**：`collect()` 末尾加 `.filter(o => o.content)`，与 `validate()` 的口径对齐（只看"填了内容的"）；
2. **错误渲染展平**：`UI.errorText()` 里加递归 `flatten()`，数组按「第 N 项：」编号、对象取所有值拼接，不再 `String(obj)`。

保留后端 `content` 必填校验是对的——接口层仍应拒绝非法数据，只是前端不该把空行发出去。

### 验证记录（2026-11-04 修复后）

`tools/verify_bug02.py` → `docs/assets/bug02_verify.txt`，8 项断言全通过：

| 场景 | 期望 | 实测 | 结论 |
|---|---|---|---|
| A 只填 2 个选项 | 保存成功，且**入库正好 2 个选项** | 创建成功，`['甲','乙']`，正确答案仍为 A | ✅ |
| B 填满 4 个 | 保存成功，入库 4 个（不能修过头） | 4 个 | ✅ |
| C 嵌套错误渲染 | 可读文案，不含 `[object Object]` | `options：第 3 项：该字段不能为空。；第 4 项：该字段不能为空。` | ✅ |

A 特意断言了"入库选项数 = 2"：只断"保存成功"的话，如果前端把整行选项都丢了也会通过。

- **回归守门**：`scripts/test_regressions.py::TestBug02Guard`（2 条，23s）——
  一条走 UI 验"只填 2 行能存且空行不入库"，一条验"嵌套错误可读"。BUG-02 若复发立刻红。

### 验证时的一个坑（测试环境，非产品问题）

第一次验证 C 场景**没通过**，页面渲染的仍是 `[object Object]`。原因不是没修好，而是：

**驱动用了固定 profile 复用磁盘缓存，浏览器加载的还是旧 `api.js`。** 服务端 `curl` 已经能看到 `flatten`，页面里 `UI.errorText.toString()` 却没有——前端改版后必须清缓存再验。

已加开关：`OE_FRESH_PROFILE=1`（清 profile 后启动，见 `config.FRESH_PROFILE`）。凡是本轮涉及前端改动，回归都用它跑一次。

- 守门 2 条已并入 `-m p1` 回归集。

## 四、BUG-03 组卷页单个知识点勾选无效，按知识点组卷实际不生效

| 字段 | 内容 |
|---|---|
| **缺陷标题** | 组卷工作台勾选单个知识点不生效：不刷新题池、不进组卷请求，界面却显示已勾选 |
| **环境/版本** | 本机 `127.0.0.1:8931`，Django 4.2.30，MySQL 5.6，2026-11-04 提测版 |
| **复现步骤** | 1. 以教师打开 `/papers/{id}/compose/`<br>2. 在左侧知识点树勾选任意**单个**知识点（如「顺序表」）<br>3. 观察左侧「题库池」是否刷新；再点「预览」 |
| **预期结果** | ① 题池按所选知识点收敛（可用题量变小）；② 「预览」请求携带 `knowledge_point_ids` |

| **严重程度** | 严重 |
| **优先级** | P0 |
| **影响范围** | 组卷模块的核心路径「按知识点组卷」。所有教师角色、所有试卷；影响组出的卷子是否符合教学目标，且**静默**——没有任何报错或提示 |
| **附件** | `docs/assets/bug03_repro.txt`（复现脚本 `tools/repro_bug03.py`，含四段证据） |
| **复现率** | 3/3 |
| **状态** | **已关闭（2026-11-04 验证通过）** — 7 项断言全通过，见下节验证记录 |

### 修复说明（开发侧回填，2026-11-04）

| 项 | 内容 |
|---|---|
| **根因确认** | 与你的分析完全一致：`dataset.kp` 是**空字符串**（无值属性），`!""` 恒为 `true`，监听器第一行就 return。把「属性存在性」写成了「属性值真值」 |
| **改动** | `if (!event.target.dataset.kp) return;` → `if (!event.target.hasAttribute("data-kp")) return;`。**没有改模板**（`data-kp` 保持无值属性）——改 JS 一处即可，属性选择器 `input[data-kp]` 不受影响 |
| **顺带（你的建议②）** | 题池为空时按是否选了知识点给不同文案：选了 N 个 → 「所选 N 个知识点下没有可用题目，可以少选几个或换学科试试」；没选 → 原「当前条件下题库里没有可用题目」。避免教师误以为系统坏了 |
| **接口侧复核** | 确认 `/papers/pool/?knowledge_point_ids=X` 本来就能收敛（admin 视角：不筛选 2429 → 单知识点 83 / 95 / 63）。**问题纯在前端，后端无需改动** |
| **守门** | 新增 `apps/system/tests/test_frontend_guards.py`：静态断言"监听器用 `hasAttribute`"+"不许退回 `dataset.kp` 真值判断"，另含 BUG-02 的空选项过滤与 `allow_blank` 下限。**验证过**：改回原写法 → 2 条立即失败 |
| **为什么用静态断言** | 这类缺陷的故障模式是「页面正常、功能没生效」：接口测试看不到（请求根本没发出去），人工点一遍也容易以为"题池本来就这么多"。跑 E2E 当然更真实，但 1ms 的静态守卫能在提交前拦住回退 |

### 根因

`templates/papers/compose.html` 的知识点监听器：

```js
$("kpTree").addEventListener("change", (event) => {
    if (!event.target.dataset.kp) return;        // ← 恒为 true，直接 return
    const id = Number(event.target.value);
    if (event.target.checked) state.selectedKps.add(id);
    else state.selectedKps.delete(id);
    loadPool();
});
```

对应的 DOM 是 `<input type="checkbox" value="${node.id}" data-kp>` —— **无值属性**，
所以 `dataset.kp === ""`（空字符串是 falsy），`!event.target.dataset.kp` 恒为 `true`。

一句话：把「属性存在性判断」写成了「属性值真值判断」。

### 证据链（三段，缺一不可）

| # | 证据 | 实测 |
|---|---|---|
| ① | DOM | `dataset.kp = ''`（truthy=False），而 `"kp" in dataset` 为 true |
| ② | 行为 | 真实点击勾选后，`/papers/pool/` 请求数 = **0** |
| ③ | 后果 | 「预览」请求体 `knowledge_point_ids = []` |
| ④ | 对照组 | 点「全选/清空」后 `/papers/pool/` 请求数 = 1，携带 **35** 个 id —— 证明接口支持按知识点过滤，问题只在单个勾选这一步 |

### 建议修法

```js
if (!event.target.hasAttribute("data-kp")) return;      // 判存在，不判值
// 或把模板改成 data-kp="1"（有值），保持现有判断
```
顺带建议：勾选后若题池为空，给出「该知识点下暂无题目」的明确提示（当前为空时只有一行红字）。

### 修复说明（开发侧，2026-11-04）

```js
if (!event.target.hasAttribute("data-kp")) return;    // 判「属性是否存在」
```

模板里的 `data-kp` 仍是无值属性，这种写法与它自洽，改动最小。

### 根因

前端 `templates/exam/monitor.html`：

```js
document.getElementById('exam-status').textContent = ov.computed_status_display || '';
```

而后端 `/api/v1/exams/{id}/attempts/` 的 `overview` 实测字段为：

```
applicants, avg_score, behavior, computed_status, exam, graded, in_progress,
max_score, min_score, not_started, pass_count, pass_rate, pending_grading,
started, submit_rate, submitted, timeout
```

**只有 `computed_status`（`ongoing` 这种代码值），没有 `computed_status_display`**。
`undefined || ''` 得到空串，于是徽章被清空。

### 建议修法

二选一：
1. 后端在 `overview` 里补 `computed_status_display`（与 `ExamListSerializer` 保持一致，最省事）；
2. 前端加一份 `computed_status → 中文` 映射兜底（`ongoing: '进行中'` 等）。
