### 3.2 缺陷明细

| 编号 | 标题 | 严重度 | 状态 | 影响 |
|---|---|---|---|---|
| BUG-01 | 成绩可见性两套口径：成绩单已公开答案与总分，作答明细仍为 null | 严重 | **已关闭** | 学生可在教师出分前获知逐题对错；前端两页面结论矛盾 |
| BUG-02 | 批量暂存 `items` 内重复题目 → 500，整批答案全部丢失 | 严重 | **已关闭** | 自动保存与手动保存并发/重试时，学生本批答案全丢 |
| BUG-03 | 单题 `/save/` 超时后返回 400，但自动收卷被外层事务回滚，作答停在 `in_progress` | 一般 | **已关闭** | 结算延后：教师侧显示"进行中"、`finalize` 暂被拒；已通过去掉外层事务修复 |

- BUG-01：`ExamAttempt.score_visible()` 收敛为唯一口径（`GRADED` 恒可见、`AUTO_GRADED` 看开关），`ScoreReportService` 改为委托。
- BUG-02：`save_answers()` 入口按 `paper_question_id` 去重（后写覆盖）+ `_save_answer_row()` 用 savepoint 兜跨请求并发 + 响应新增 `ignored`。验证：同题 ×2 → `200/saved=1`，落库为后者；混批不丢正常项。
- BUG-03：去掉 `save_answer()` 的 `@transaction.atomic`，与批量入口共用同一事务边界。验证：超宽限单题保存 → `400/10400` 且状态 `timeout`；正常路径仍 `200/saved=1`。

## 4. 覆盖分析

### 4.1 接口覆盖

| 项 | 数量 | 说明 |
|---|---|---|
| 接口操作总数 | 124 | 以 `manage.py spectacular` 导出的 OpenAPI 为事实基线 |
| 有直接用例 | 105 | 脚本中明确调用了该 `method + path` |
| 同源合并覆盖 | 19 | PUT/详情/选择器类，与同资源 PATCH、创建响应体共用序列化器与 service；另有既有契约矩阵（124 操作 × 4 身份 + 非法参数，661 断言）兜底 |
| 完全未覆盖 | **0** | 逐条理由见 `04-测试用例.md` §20 |

### 4.2 主链路覆盖（10/10）

登录鉴权 → 建知识点/题目 → 组卷 → 发布 → 建考试并发布 → 开考 → 暂存/心跳/行为上报 → 交卷 → 判分（客观自动 + 主观 AI）→ 复核 → 出分 → 成绩单/明细 → 学情/趋势/诊断 → 推荐 → 监考证据链 → 班级管理，全链路有自动化串联用例（`test_l0b_flow.py`）并断言跨接口一致性。

### 4.3 安全与一致性横切

- 答案与解析字段：学生侧所有可访问接口递归扫描，出现即失败；
- 判分类字段（`is_correct`/`score`/`ai_score`/评语）：未出分必须为 `null`，出分后两接口结论必须一致；
- 越权：跨学生、跨班级、跨学科、班外开考、非班主任改班等 21 组矩阵；
- 时间权威：客户端上报剩余时间不生效，服务端 `deadline_at` 为准；
- 写入幂等：同一题重复提交合并（BUG-02 回归）、重复交卷/判分/出分幂等；
- 限流：登录 30/min 生效，且不误伤已登录接口。

## 6. 上线风险评估结论

**结论：可以上线。**

判定依据：

1. **3 条缺陷全部关闭**，且每条都有转正后的回归用例守门，套件内无 xfail 残留：
   - BUG-01（可见性双口径）→ 断言两接口结论一致；
   - BUG-02（批量暂存重复题 500）→ `同题×2 → 200/saved=1`、混批不丢正常项；
   - BUG-03（单题超时结算延后）→ 超宽限单题保存返回 400 且状态落 `timeout`。
2. 功能面与安全面无未闭环问题：229 条断言覆盖 124 个接口、10 条主链路、21 组权限矩阵，答案/评分字段有横切白名单守门；
3. 套件稳定可复跑：229 条 / 49–53 秒，连跑多轮结果一致，适合作提测门禁；
4. 性能与兼容性本轮未覆盖，需引用既有报告或补测——这是本轮唯一未验证的质量维度。

放行建议：

- **可以直接上线**，无阻塞项；
- 上线后一周内建议关注两类指标：① "超时未结算"的作答数量（`status=in_progress` 且 `deadline_at` 已过）；② 作答接口的 5xx 比例（BUG-02 类写入异常的表现形式）；
- 若并发交卷场景占比高，建议补一轮 20 并发的交卷压测再放量。

## 7. 改进建议

### 7.1 开发侧

1. 列表型写接口统一"入口去重 + savepoint 兜底"（作答、批量加题、批量调分同源），抽公共函数复用；
2. 事务边界要跟着"业务动作"走：结算类副作用不应被后续业务拒绝回滚（BUG-03 就是外层事务把收卷吞了）；
3. 分页参数口径已在 `StandardPagination` 统一（`page` 非法 400、超范围 404），建议其余手写列表接口也复用该类；
4. 可见性规则只允许住在模型层（`ExamAttempt.score_visible()`），其余调用方一律委托——BUG-01 的根因就是"两处各写一遍"。

### 7.2 测试侧

1. 补 `clean_at_data.py`，把 `at_` 前缀数据按 run 归档，控制库体量；
2. 增加"AI 超时/降级"与"并发交卷"两个专项：前者用超时配置或 monkeypatch，后者用 20 并发小压测；
3. 契约测试（124 操作 × 4 身份）与本套件合并进一条流水线：契约保准入，本套件保业务；
4. 用例必须幂等：唯一约束字段（用户名、题干）一律带运行期后缀，本轮已修 8 条。

### 7.3 流程侧

1. 提测准入增加"`pytest` 全绿 + 无 500"门禁，53 秒可跑完，成本极低；
2. 缺陷回归用例与被测代码同仓（`apps/*/tests/`）已在做，建议把本套件已转正的 3 条缺陷回归用例同步一份到开发仓，缩短反馈环；
3. 文档与实现出现口径差异时，以"实测 + 用例"为准回写文档，本轮累计修正 8 处。
